🔌 Teste de acesso ao Ollama — dentro do VPL

Este bloco roda no navegador do aluno. Ele não fala com 127.0.0.1:11434: aponte para um serviço HTTPS no vision (proxy do Ollama ou gateway) que encaminhe para o guiou-Dell. Se a página do VPL é HTTPS, a URL do serviço também precisa ser HTTPS.

O que este teste verifica: se o navegador consegue alcançar o serviço (GET), se o CORS/preflight está correto (POST) e se o modelo responde. O JSON bruto aparece no fim para facilitar o diagnóstico.
Pronto. Ajuste a URL e clique em “Testar conexão”. 
(a saída aparece aqui)
Se der erro, veja o checklist
  • Página HTTPS + URL HTTP → o navegador bloqueia (mixed content). Use HTTPS no serviço.
  • “Failed to fetch” → pode ser CORS, DNS, rede ou servidor fora do ar. Confira a aba Console/Network do navegador (F12).
  • CORS → o serviço precisa responder Access-Control-Allow-Origin para a origem do Moodle e tratar OPTIONS (o POST JSON dispara preflight).
  • 404 → caminho errado. Confira /api/chat, /api/generate ou /v1/chat/completions.
  • 401/403 → token/permissão. Preencha o campo Token ou ajuste o proxy.
  • Timeout → o modelo pode estar carregando na GPU; tente de novo ou use um modelo menor.
  • GET funciona, POST falha → quase sempre é o preflight CORS do OPTIONS.
  • CSP → a página do Moodle pode bloquear conexões para outro domínio (connect-src). Veja o Console (F12).
  • O editor do VPL removeu o <script> → teste a versão standalone; se necessário, use um link/iframe para a página do teste.

Dica: para testar o Ollama no seu computador, use a URL http://localhost:11434 e o tipo “Ollama — /api/chat”. No VPL de produção, use o proxy HTTPS do vision. Não embuta o token no HTML em produção: o aluno consegue vê-lo; use o campo Token apenas no teste.
