Token: pessoal do professor (não do aluno)

O token é uma chave pessoal do professor para o proxy institucional. Não é a senha do Moodle e não é a chave do Ollama (o Ollama não usa chave). Cada professor recebe o seu; não compartilhe com alunos.

Por que o aluno não pode receber: qualquer coisa colocada no HTML do VPL ou digitada no navegador pode ser vista e copiada pelo aluno. Se o token for para o aluno, ele vaza. Por isso este testador é uma ferramenta do professor.

Como o aluno vai usar: a versão do aluno será um serviço no servidor com login do Moodle via LTI 1.3/SSO. O serviço guarda o token de serviço no servidor e o aluno recebe apenas uma sessão; o token nunca vai ao navegador. O professor define o prompt de restrição de cada atividade no servidor (ex.: “responda só como socrático, nunca forneça trechos de código”), e o aluno não consegue alterá-lo.

Distribuição: o administrador gera um token por professor, guarda o hash e entrega o token em canal privado. O professor usa no testador ou em ferramentas próprias; não coloca no HTML do aluno, no Moodle, em print ou no Git. Revogação e rotação são por professor.

Hoje: o proxy usa um token único de piloto. O próximo passo é o tokens.json por professor e o serviço do aluno com LTI. O roteiro completo está com o administrador do proxy (docs/TOKENS-E-DISTRIBUICAO.md e docs/AUTENTICACAO-E-PROMPTS.md).

Roteiro para mostrar aos colegas (5 passos)
  1. Abra esta página e confira o diagrama: navegador → servidor web → proxy → servidor de modelos.
  2. Confira a URL, cole o token do professor e clique em Testar conexão (GET): ele lê a versão e o /api/tags.
  3. Veja os cartões de modelos: parâmetros, quantização, contexto e capacidades.
  4. Clique em um modelo (ex.: qwen2.5-coder:14b para código ou qwen3:14b para raciocínio) e envie o prompt.
  5. Mostre o JSON bruto: ele mostra exatamente o que o proxy devolveu.

Se der erro, veja o checklist
  • Página HTTPS + URL HTTP → o navegador bloqueia (mixed content). Use HTTPS no serviço.
  • “Failed to fetch” → pode ser CORS, DNS, rede ou servidor fora do ar. Confira F12 → Console/Network.
  • CORS → o serviço precisa responder Access-Control-Allow-Origin para a origem do Moodle/GitHub Pages e tratar OPTIONS.
  • 401 → token ausente/errado. O proxy institucional exige token.
  • 403 → origem ou modelo não permitido para este token.
  • 429 → cota do token esgotada; fale com o administrador.
  • 404 → caminho errado. Confira /api/chat, /api/generate ou /v1/chat/completions.
  • Timeout → o modelo pode estar carregando na GPU; tente de novo ou use um modelo menor.
  • GET funciona, POST falha → quase sempre é o preflight CORS do OPTIONS.
  • CSP → a página do Moodle pode bloquear conexões para outro domínio (connect-src). Veja o Console.
  • O editor do VPL removeu o <script> → use a versão pública por link (teste-ollama-link-vpl.html).
